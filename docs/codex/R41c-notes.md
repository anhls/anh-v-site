## Findings (mechanism)
1. RENDERER DESTROYED AT FLICK START (proven with probe.mjs): on lite the first drag move (and every wheel) called disposePrepared(true), which RELEASES the spare WebGL renderer: WEBGL_lose_context.loseContext() 21 ms after touchstart, inside the first flick frames, and the prepared renderer is gone; the next rest builds a NEW WebGL context + shader + texture, which can land on the next flick. On iOS a context loss / creation is a ~100-200 ms main-thread task, which matches the 170-200 ms freezes at the start of flicks. Before: loseContext at 5345 ms (touch at 5324), prepared canvas gone. After: no loseContext, prepared canvas stays "ready".
2. GUARD (a likely cause of the plain fallback): the frame-time guard stepped on ONE bad burst (a p95 over 30 ms; one 180 ms stall is enough). Step 3 = warp off = the tap gate's "degraded" = plain page load. The recording's plain open fits this. Not proven: the report will say.
3. TITLE: the DOM title faded per frame with dt (a stalled frame leaves it half faded: the grey text under the picture) and the smear texture (2D canvas text + texImage2D) was built inside play() at the settle.

## Changes
- core.js: drag / wheel call disposePrepared() without release (cancels the preparation and parks the renderer; resize, hidden and pagehide still release). Idle work (prepare, header decode prefetch) already waits for rest (idleMs 600) and is cancelled on the first drag move; unchanged.
- tall-title.js: leave = CSS opacity transition (titleOutSec; compositor, time based, no per-frame work); at true rest the textures of the settled project and its neighbours (0, +1, -1, +2, -2) are built ahead, ONE per task, 90 ms apart, cancelled when the strip moves.
- smear.js (shared, additive): a texture cache plus warm(o). A cache miss builds exactly as before; drawGl binds run.tx.tex. Desktop title output is unchanged (desktop checks below).
- tall-guard.js: the guard counts only SUSTAINED slowness: ignores the first 3 s after load, a single frame over 120 ms and the 2 frames after it; a median over 20 ms steps at once, a p95 over 30 ms must repeat in two bursts in a row. Test (guardtest.mjs): 12 flicks each with a 200 ms stall: step 0, warp on; 12 flicks with 35 ms frames: steps 1, 2, 3.
- Snap, what it does today on touch: while a finger is down (drag) or the strip coasts (inertia) lastWheel is refreshed every frame and snap is null, so the soft snap cannot engage under a finger or during momentum (already so). A fling plans its own landing exactly on a project (flingPlan), so it cannot pull back. Only a sub-fling release is paged by the soft snap to the NEAREST project within half a pitch; that can move up to half a pitch back toward the previous project. Left as is (the paging feel); measured on 14 flicks: 0 flicks retreat more than 12 px (retreatPx 0-7). Say if you want forward-only paging for slow releases.
- Not changed: the jump after a freeze is the catch-up of the time-based inertia after a stall; it goes with the stall.

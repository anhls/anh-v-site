## R24i (phone / tablet: project images fill the frame without distortion; Work page image warp: the cylinder leans toward the direction the images are moving) (use Sonnet 5.5, quick mode, AFTER R24h: both change the warp buffer / pass)
Anh's idea. Today the image warp's cylinder axis is fixed at the screen centre (frame-warp-shader.js: the sheet is flat up to the middle `reach`, then curls both ways around the centre line; the sign of `uAmt` only decides which side recedes). New: the axis MOVES along the strip in the direction the images are visibly travelling on screen, by an amount that grows with the warp strength (so the more speed, the more it leans). Rule (Anh): the centre of the warp moves toward where the strip is going on screen. Desktop: wheel DOWN moves the strip from right to left (side mode), so the axis moves LEFT; wheel up = right. Phone / tablet: the strip moves along the flick direction (finger up = images up = the axis moves UP, finger down = down; the horizontal tablet strip the same left / right). Vertical desktop strip: the same rule, by the real on-screen motion. At rest the axis is exactly back at the centre. Applies to the Work page MAIN IMAGE warp in every mode (desktop side, desktop vertical, phone / tablet lite). The homepage frame warp and the cards' warp (warp-shader.js, home frame) are NOT touched.
0. FIX FIRST (Anh, real phone and tablet): on the phone and tablet the project images look STRETCHED AND SQUASHED to meet the desktop ratio (the lite frame is forced to `frameRatio()` 1.6232, but the source pictures have other aspects). He wants the image to FILL the frame (object-fit: cover: scaled uniformly until the frame is covered, the overflow cropped, centred), never distorted. The GL path already has `uCover` (cards-gl.js setCover: scaleU / scaleV / offU / offV from the source aspect) and the flat DOM fallback has `object-fit: cover` (work.css `.work__item img`), so find where the lite frame goes wrong: the likely causes are (a) the frame's quad is drawn at one size and setCover is given another (the aspect used for the cover maths taken from the DOM box / the desktop frame size instead of the lite frame's real w x h, or from a stale size after `liteFrame` / a resize / the first layout), (b) the source aspect read before the image has loaded (aspect[i] = 1, line 266) and never refreshed, (c) a non-uniform scale in the frame transform (focus scale, warp pass margins uMargin, or the vertical / horizontal axis swap) so the image is stretched on one axis.
